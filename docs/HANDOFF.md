## 1. Идея проекта

**Way Market** — продуктовый магазин в Грозном, работает 24/7. Нужна **одна CRM-система** вместо разрозненных
программ (старый каталог WayMarket, учёт и финансы Auron Finance и другие — список в `docs/TZ.md`, раздел 3).

Кто пользуется:
- **владелец** — всё видит и управляет, выдаёт доступы;
- **управляющий, бухгалтер** — работа с товарами, деньгами, людьми;
- **сотрудники** — смены, задачи;
- **поставщики и торговые представители (ТП)** — свои заказы, долги, сверки;
- **покупатели** — каталог, списки покупок, отзывы.

Где работает: **на любом ПК (браузер), на Android и iPhone (устанавливается как приложение) и внутри Telegram**
(Mini App бота). Это одно приложение и один код.

Главные требования владельца:
1. **Безопасность и конфиденциальность** — защита от взлома, кражи, утечки; закрыть все уязвимости.
2. **Расширение и переезд** — новые модули без переделки старых; переезд на свой сервер без переписывания.
3. **Бесплатный хостинг** — сайт на GitHub Pages, сервер — Supabase (сейчас тестовый проект).
4. **Дизайн в стиле iPhone** — минимализм, эстетика, премиум, без потери функций (раздел 6).
5. **152-ФЗ**: настоящие персональные данные покупателей и сотрудников — только на сервере в РФ.

Полное техническое задание — `docs/TZ.md` (этапы 0–7, критерии приёмки, вопросы владельцу).

## 3. Стек и устройство

- **Интерфейс**: React 19 + TypeScript (strict) + Vite, PWA (vite-plugin-pwa), Telegram Mini App.
  Папка `web/`. К серверу обращается **только** `web/src/api/` (правило линтера).
  Детали интерфейса — `web/src/shared/ui/`, тексты — `web/src/shared/i18n/ru.ts`.
- **Сервер**: Supabase (PostgreSQL + Auth + Edge Functions). Схема — только миграциями в `supabase/migrations/`.
  RLS на всех таблицах, по умолчанию запрещено; изменения прав и денег — через серверные функции (RPC).
- **Вход**: через Telegram без паролей. Edge Function `supabase/functions/auth-telegram` проверяет подпись
  `initData` токеном бота (секрет `TELEGRAM_BOT_TOKEN` только в Supabase), создаёт учётку
  `tg<id>@telegram.invalid` и выдаёт сессию. Владелец, управляющий, бухгалтер — плюс код из приложения-
  аутентификатора (TOTP); без кода их права в базе не действуют (уровень сессии `aal2`).
- **CI** (`.github/workflows/`): линтер, типы, тесты, сборка, `npm audit`; тесты прав базы на локальном
  Supabase; Deno-тесты и сквозной тест входа; gitleaks; CodeQL; выкладка сайта на GitHub Pages.
  Сторонние действия закреплены по хэшу коммита.

```
web/src/api/            связь с сервером (auth, team, mfa, client)
web/src/modules/common/ учётная запись, вход, второй фактор
web/src/modules/staff/  экран «Команда»: приглашения, участники
web/src/modules/catalog/ каталог: поиск (search.ts), экран, карточка, фото, перенос старого каталога и его фото
web/src/api/openFoodFacts.ts  открытая база Open Food Facts: фото по штрихкоду
web/src/shared/         ui (дизайн iOS), i18n, деньги, телефоны, даты, Telegram
supabase/migrations/    core → … → catalog → catalog_import → catalog_version → product_photos → photo_source
supabase/functions/     auth-telegram + _shared/telegram-init-data.ts
supabase/tests/         run.sh, *_test.sql (права), auth_telegram_e2e.mjs (сквозной вход)
```

## 5. Что получилось и что не получилось (уроки)

- Получилось: вход без паролей с проверкой подписи; права на уровне базы (интерфейс можно обойти, RLS — нет);
  каждый шаг покрыт тестами и проверен в браузере; CI ловит ошибки до слияния.
- Токен бота однажды попал на скриншот и был отозван; после отзыва забыли обновить секрет — вход отвечал
  «Telegram не подтвердил вход». Теперь функция пишет причину в журнал (Supabase → Edge Functions → Logs).
- В Telegram после выкладки сначала открывается старая версия из кэша; новая подтягивается плашкой
  «Доступна новая версия» → «Обновить». Это нормально (PWA), предупреждай владельца.
- Тест нашёл ошибку на границе срока приглашения (`<` вместо `<=`) — исправлено миграцией team.
- Инструмент Supabase `apply_migration` (MCP) зависает на `DROP …`: ждёт ручного подтверждения владельца.
  Пиши миграции без `DROP` (временные таблицы заменяй запросом с `with`), иначе применять будет некому.
- Тесты базы считают видимые магазины: на локальной базе с открытым каталогом (`catalog_public = true`)
  они падают — перед `run.sh` скрой такой магазин или запускай на чистой базе (как в CI).
- Локальный стенд Supabase в песочнице не мог скачать npm-пакеты через прокси — решалось локальным зеркалом;
  в обычной среде и в CI этого нет.
- Владелец — не программист. Пиши по-русски, просто, по пунктам; ручные шаги — с точными названиями кнопок.
  Никогда не проси прислать токен, пароль или ключ в чат.

## 6. Стиль (обязательно)

## 7. Безопасность (не нарушать)
- Репозиторий публичный: никаких токенов, паролей, ключей, адресов серверов, настоящих персональных данных.
  Перед коммитом — gitleaks (он есть в CI). Тестовые данные — вымышленные (телефоны `+7900000000x`).
- Новая таблица = миграция + RLS + тест прав в одном PR. Права и деньги — только через RPC с проверкой роли.
- Секреты — только в Supabase → Edge Functions → Secrets или в настройках GitHub; в чат — никогда.
- Настоящие данные людей — только после переезда на сервер в РФ (вопрос 3).

## 9. Как работать в репозитории
1. Ветка от свежего `main` → изменения → локальные проверки:
   `cd web && npm run lint && npm run typecheck && npm test && npm run build`;
   база: `npx supabase@2.119.0 start …` и `supabase/tests/run.sh`; функции: `deno check`, `deno lint`, `deno test`;
   сквозной вход — `docs/DEPLOY.md`.
2. PR → CI зелёный → слияние. Владелец разрешил исполнителю сливать самому после зелёного CI
   («настрой все сам»); если сомневаешься — спроси.
3. Миграции к тестовому проекту применять после слияния сайта, если новый сайт без них работает
   (так было со вторым фактором), иначе — до.
4. После каждого шага: обновить `docs/PROGRESS.md`, при решениях — `docs/DECISIONS.md`, и **этот файл**.
